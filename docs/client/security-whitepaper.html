🔒 1. Authentication

All API requests are authenticated via JSON Web Tokens (JWT) using the HS256 (HMAC-SHA256) signing algorithm. Tokens are passed in the Authorization: Bearer <token> header on every request.

Secret Enforcement

The server enforces a minimum JWT secret length of 32 characters at startup. If the configured secret is shorter, the server refuses to start, preventing weak-key deployments.

Development Mode

An AUTH_DISABLED environment variable is available for local development only. When set, the server emits a prominent startup warning to stderr and skips token validation. This flag has no effect when the binary is compiled in release mode with the production feature gate.

👥 2. Authorization (RBAC)

Role-Based Access Control is enforced at the handler level. The JWT middleware extracts claims and injects them into the request extensions. Handlers that perform destructive operations call require_admin(), which returns 403 Forbidden if the caller's role claim is not admin.

⚡ 3. Rate Limiting

The API implements a token-bucket rate limiter applied per source IP address to prevent abuse and ensure fair resource allocation.

Rate Limit Parameters
ParameterValue
AlgorithmToken Bucket
Burst capacity100 requests
Sustained rate50 requests/second
GranularityPer source IP
Bucket cleanup interval60 seconds

Implementation Details

  • Stale buckets (IPs that have not made requests recently) are purged every 60 seconds by a background task to prevent unbounded memory growth.
  • The bucket map is protected by a Mutex. If the mutex is poisoned (a previous holder panicked), the rate limiter recovers gracefully by replacing the poisoned lock rather than propagating the panic to all subsequent requests.
  • Clients that exceed the limit receive 429 Too Many Requests with a Retry-After header.

🔌 4. WebSocket Security

WebSocket connections are used for real-time streaming of network flows and metrics. Security controls are applied at both upgrade time and during the connection lifecycle.

Connection Limiting

A global maximum of 100 concurrent WebSocket connections is enforced. New upgrade requests beyond this limit receive 503 Service Unavailable. This prevents resource exhaustion attacks via connection flooding.

Authentication on Upgrade

WebSocket upgrade requests pass through the same JWT authentication middleware as standard HTTP requests. The Authorization header must be present on the initial HTTP upgrade request. Tokens are validated before the protocol switch occurs.

Streams

  • /ws/flows — real-time Cilium network flow events
  • /ws/metrics — live metric updates (node, pod, policy stats)

📜 5. Input Validation

Kubernetes Resource Names

All user-supplied Kubernetes resource names are validated against RFC 1123 DNS label rules: lowercase alphanumeric characters and hyphens, must start and end with an alphanumeric character, maximum 63 characters. Invalid names are rejected with 400 Bad Request before any cluster interaction occurs.

Resource Kind Allowlist

Policy operations accept only a strict allowlist of Kubernetes resource kinds:

  • CiliumNetworkPolicy
  • CiliumClusterwideNetworkPolicy
  • NetworkPolicy (Kubernetes native)
  • CiliumEgressGatewayPolicy

Requests specifying any other kind are rejected, preventing injection of unexpected resource types into the cluster.

YAML Injection Prevention

All user-supplied string values embedded into generated YAML policy documents are sanitized through a dedicated yaml_escape() helper function. This function escapes special YAML characters (colons, quotes, newlines, anchors, aliases) to prevent attackers from injecting additional YAML directives or altering the structure of generated policies.

🌐 6. Network Security

CORS

Cross-Origin Resource Sharing is configured with an explicit origin allowlist. Wildcard origins are not permitted. The allowlist is configurable at startup via environment variable, defaulting to the dashboard's origin only.

Compression

HTTP responses are compressed (gzip/brotli) via tower middleware to reduce bandwidth and mitigate data exfiltration volume in the event of a compromised session.

TLS

TLS termination is handled at the ingress layer (Kubernetes Ingress or load balancer). The API server binds to a local interface and expects TLS to be terminated upstream. In production deployments, all external traffic is encrypted in transit.

🗃 7. Data Security

Caching

The platform uses Redis as an optional caching layer. Cache entries have a configurable TTL (time-to-live), defaulting to short durations appropriate to the data type. Cache keys are derived from API path and query parameters only — no user-specific data is included in keys.

Data Classification

  • No Personally Identifiable Information (PII) is stored or cached by the platform.
  • Cached data consists of Kubernetes resource metadata, Cilium policy state, and flow statistics.
  • JWT tokens are validated but never persisted to disk or cache.

Secret Handling

JWT signing secrets should be provided via environment variable or mounted secret. Operators are advised to enable zeroization of the secret from memory upon server shutdown using the zeroize crate pattern, preventing cold-boot recovery of key material.

📦 8. Supply Chain Security

Memory Safety

The entire API server is written in Rust, providing compile-time guarantees against buffer overflows, use-after-free, double-free, and data races. These vulnerability classes account for approximately 70% of CVEs in C/C++ network services.

Unsafe Code Audit

The application codebase contains no unsafe blocks in application logic. The only unsafe usage is a single libc::close() call for file descriptor cleanup, which is guarded by a validity check (fd > 2) to prevent closing stdin/stdout/stderr.

Dependency Auditing

Dependencies are audited using cargo-audit against the RustSec Advisory Database. The CI pipeline fails on any known vulnerability in the dependency tree. Cargo.lock is committed to ensure reproducible builds.

Security Posture Scoring

The platform computes a real-time security posture score (0–100) based on policy coverage, encryption status, and configuration compliance. This score is surfaced in both the web dashboard and the TUI.

Audit Logging

All state-changing operations (policy CRUD, node operations, chaos experiments) are logged with timestamp, actor identity (from JWT sub claim), action, target resource, and outcome. Logs are emitted in structured JSON format suitable for ingestion by SIEM systems.
